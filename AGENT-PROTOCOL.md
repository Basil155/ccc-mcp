# ccc-mcp (Command Claude Code) — протокол для вызывающего агента

> **Производный файл.** Источник истины — [`docs/protocol.md`](docs/protocol.md),
> [`docs/permissions.md`](docs/permissions.md), [`docs/tools.md`](docs/tools.md).
> При их правке синхронизировать этот файл.

Этот файл адресован ИИ-агенту, который вызывает инструменты моста `ccc-mcp`, а не человеку,
который его устанавливает. Здесь только то, что нужно для правильного действия: императивные
правила, значения полей и реакция на каждое. Обоснования «почему именно так», установка и
настройка — в `README.md`, `SETUP.md` и `docs/`.

Файл самодостаточен: его можно целиком вставить в системный промпт или в `CLAUDE.md` целевого
проекта.

## Обязательный цикл

```
plan_task  →  показать план пользователю  →  approve_plan  →  execute_task
 planned                                       approved      executing → executed
```

| Шаг | Вызов | Что приходит в ответе |
|---|---|---|
| 1 | `plan_task(task_text, project_dir)` | `session_id`, `plan_digest`, `session_state: "planned"` |
| 2 | `approve_plan(session_id, plan_digest)` | `session_state: "approved"` |
| 3 | `execute_task(task_text, project_dir, session_id)` | отчёт о работе, `session_state: "executed"` |

Правила:

1. **`plan_task`** — получить план. Отправляй сюда только «спланируй», не «выполни»: это
   разведка, а не песочница. Правку файлов режим плана запрещает, но Bash-команды
   выполняются по правилам разрешений пользователя, поэтому при включённом контроле
   разрешений они и здесь приходят в `permission_requests` — веди их так же, как для
   `execute_task`. Команду, которая что-то меняет, на этапе плана не одобряй.
2. **`has_open_questions: true` — план не одобрять.** Задай пользователю вопросы из раздела
   «Открытые вопросы» в `result_text`, получи ответы, вызови `plan_task` заново с уточнённой
   формулировкой. `approve_plan` и `execute_task` для такой сессии откажут.
3. **Иначе покажи пользователю `result_text` целиком** и дождись явного согласия.
4. **`approve_plan`** — `session_id` и `plan_digest` бери из ответа `plan_task` без изменений.
5. **`execute_task`** — тот же `session_id` и тот же `project_dir`, что и при планировании.
6. **Если прокси теряет `session_id`** (ошибка `-32602 … received undefined at session_id`, хотя
   ты его передал), передай то же значение под синонимом `session`. Его принимают все три
   инструмента; одновременно оба имени передавать не нужно, а если передаёшь, значения должны
   совпадать.
7. **`status: "running"`** — опрашивай `get_task_status(process_id, wait_seconds)` до завершения.

Что нужно помнить между вызовами:

* **`execute_task` без одобренного `session_id` невозможен.** Запустить задачу «с нуля», минуя
  план, нельзя.
* **Повторный `plan_task` сбрасывает одобрение** и меняет `plan_digest`. Старый дайджест
  перестаёт подходить.
* **После успешного выполнения нужен новый цикл** — одобрение израсходовано.
* **Сбой одобрение не сжигает.** После таймаута, отмены или ошибки API сессия остаётся
  `approved`, попытку можно повторить.
* **Одобрение привязано к каталогу.** `project_dir` в `execute_task` должен совпадать с тем,
  для которого строился план.
* **Пока задача идёт, одобрение занято** (`executing`): параллельный `execute_task` по той же
  сессии будет отклонён.
* **Одна сессия — одна идущая задача.** Не запускай `plan_task` или `execute_task` с
  `session_id`, по которому ещё идёт другая задача: вызов отклонят с её `process_id`. Дождись
  её через `get_task_status` или останови `cancel_task`, потом повтори. Не обходи отказ
  параллельным запуском без `session_id` — это будет уже другая, пустая сессия.
* **Состояния живут в памяти сервера.** После перезапуска одобрения теряются, цикл нужно пройти
  заново.
* **Успех определяй по полю `ok`, а не по `subtype`.** `subtype` бывает `"success"` при
  фактическом провале. Поле `next_step` называет следующий шаг.

## Выбор модели

`model` есть у `plan_task` и `execute_task`: алиас (`opus`, `sonnet`, `haiku`) или полное имя.
Без него берётся модель из конфига моста, а если и там пусто — модель выбирает сам CLI.

* **Модель можно менять между шагами.** Одобрение привязано к тексту плана и каталогу, а не к
  модели: планировать можно одной, выполнять другой.
* **Алиас `haiku` мост заменяет на полное имя** (`model_requested` покажет `claude-haiku-4-5`).
  Иначе Claude Code в режиме плана тихо планировал бы на Sonnet.
* **Что отработало на самом деле — в `model_used`.** Если оно не совпадает с `model_requested`,
  скажи пользователю.
* Для простых планов с чётко поставленной задачей хватает `haiku`, это в разы дешевле.
  Для разведки по незнакомому коду и нетривиальных изменений бери модель сильнее.

## Долгие задачи

`plan_task` и `execute_task` возвращают `status: "running"` и `process_id`, если не уложились
в `wait_seconds`. Дальше — `get_task_status(process_id, wait_seconds)`.

`wait_ended_reason` говорит, почему вернулось ожидание:

| Значение | Реакция |
|---|---|
| `completed` | Задача закончилась. Читай `ok` и `result_text`. |
| `timeout` | Задача идёт. Опроси `get_task_status` ещё раз. |
| `pending_permission` | Появились операции, ждущие решения. Разбери `permission_requests` немедленно. |
| `null` | Ожидания в этом вызове не было. |

**Стоимость известна только по завершении:** пока задача идёт, `total_cost_usd` равен `null`.
Не отчитывайся пользователю о стоимости раньше времени и не подставляй вместо неё
`progress.last_result_cost_usd` — это промежуточное значение по последнему завершившемуся
сегменту, а не итог.

Что показывать пользователю из `progress`, пока задача идёт:

* `last_assistant_text` — последнее видимое сообщение модели;
* `tools_used` и `last_tool_call.summary` — что делается;
* `idle_seconds` — не застряла ли;
* `recent_events` — лента последних событий.

## Разрешения (при `hooksEnabled: true`)

По умолчанию выключено, и тогда `permission_requests` всегда приходит пустым — раздел можно
пропустить. Когда включено, в середину третьего шага встраивается ещё один:

| Шаг | Вызов | Что приходит в ответе |
|---|---|---|
| 3 | `execute_task` | `status: "running"` |
| 3a | `get_task_status` | `permission_requests` с `decision: "pending"` — операция ждёт решения |
| 3b | `approve_permission_request` | `decision: "approved"`, удерживаемый вызов проходит сразу |
| 3c | `get_task_status` | отчёт о работе, `session_state: "executed"` |

```json
{ "name": "approve_permission_request",
  "arguments": { "process_id": "6f0c…", "request_id": "a1b2c3d4e5f6",
                 "decision": "allow", "reason": "тесты запускать можно" } }
```

Порядок действий:

1. **Опрашивай `get_task_status`, пока задача выполняется.** Запрос на разрешение возникает
   в середине прогона, и `next_step` в этот момент прямо говорит, что нужно решение.
2. **Показывай запрос пользователю.** `summary` содержит саму команду или путь к файлу — этого
   достаточно, чтобы человек понял, на что соглашается.
3. **`request_id` бери из ответа, не придумывай.** Это отпечаток самого вызова: угадать его,
   не увидев запрос, нельзя.
4. **После `approve_permission_request` обязательно переопроси `get_task_status`.** Без этого
   задача так и будет висеть в глазах пользователя, хотя дочерний процесс уже пошёл дальше.
5. **Решай в окне удержания.** Мост держит вызов открытым до `permissionHoldSeconds` (по
   умолчанию 120 с). Решение в это окно отвечает удержанному вызову сразу, и операция проходит с
   первой попытки. Поэтому ставь `wait_seconds` у опросов — ожидание прервётся досрочно, как только
   появится запрос, — и сразу неси запрос пользователю.
6. **Не тяни.** Не успел в окно — мост отвечает отказом с просьбой повторить, а следующая попытка
   удерживается снова. После `retryBudget` отказов (по умолчанию 10) операция запрещается до
   конца задачи, и Claude Code продолжит без неё.

`denied_count` в записи — сколько раз хук уже ответил отказом. Одобренный с первого раза вызов
показывает `0`; растущее число значит, что окно удержания раз за разом пропускается.

Автоодобренный вызов в `permission_requests` не появляется вовсе — решать по нему нечего.

## Что делать по `pattern` из диагностики

Когда мост распознал ситуацию, `next_step` содержит готовую фразу с `process_id`, именем
инструмента и рекомендацией. Код ситуации — в `pattern`:

| `pattern` | Действие |
|---|---|
| `permission_exhausted` | Операция запрещена до конца задачи; одобрение задним числом уже ничего не изменит. Сообщи пользователю: дождаться неполного результата или `cancel_task` и перепланировать. |
| `permission_retry_loop` | Реши немедленно — модель жжёт `retryBudget` на повторах одного и того же вызова. |
| `permission_flooding` | Не одобряй по одному. Покажи список пользователю, рассмотри `cancel_task` и уточнение задачи. |
| `pending_permission` | Покажи запрос пользователю → `approve_permission_request` → переопроси `get_task_status`. |
| `no_progress` | Ждать бесполезно: `cancel_task`, смотреть stderr в логе. |
| `repeated_tool_call` | Покажи пользователю `last_tool_call` и `recent_events`, реши с ним про `cancel_task`. |
| `rate_limited` | Отмена и перезапуск не помогут. Опрашивай `get_task_status` с большим `wait_seconds`. |
| `stalled` | Похоже на зависание. Покажи `recent_events`, предложи `cancel_task`. |
| `thinking_only` | Опроси ещё раз; при повторе той же картины обсуди отмену и более конкретную постановку задачи. |
| `tool_running` | Ничего не делай и не отменяй — инструмент физически выполняется. |

## После `cancel_task`

* **`result_text` всегда `null`.** Итоговый отчёт CLI мост не подделывает, и одобрять как план
  тут нечего.
* **Смотри `hint`** — он перечисляет, что успело произойти: длительность, вызовы инструментов,
  последний вызов, ходы ассистента, последнее видимое сообщение.
* **Смотри `progress.recent_events`, `tools_used`, `last_tool_call`** — подробности.
* **`session_id` сохранён.** Ту же сессию можно продолжить новым циклом
  `plan_task` → `approve_plan` → `execute_task`, передав его на вход.

То же верно для `status: "timeout"`.

## Вне протокола: файлы и git

Этим инструментам не нужны ни `session_id`, ни одобрение: это прямые операции моста без запуска
Claude Code. Границы у них те же — `allowedRoots`, а `path` обязан быть относительным путём
внутри `project_dir`.

**Файлы.** Нужно просто показать пользователю содержимое (`CLAUDE.md`, `SKILL.md`, конфиг) или
положить обратно согласованную с ним версию — используй `read_project_file(project_dir, path)` и
`write_project_file(project_dir, path, content)`. Гонять это через `plan_task`/`execute_task` —
лишние токены и минуты.

* `write_project_file` **перезаписывает файл целиком**, а не патчит: сначала прочитай его,
  покажи пользователю новую версию, только потом пиши.
* В ответе записи придёт `previous.content` — покажи по нему, что изменилось.
* Точный путь неизвестен — начни с `list_project_files(project_dir)`: он вернёт дерево без
  `node_modules`, `.git` и прочего игнорируемого, а `path` из его ответа подставляется в чтение
  и запись без правки.
* Поиск по имени — `name_contains` (например `"claude"` найдёт `CLAUDE.md`) и `extensions`.
  Пришло `truncated: true` — сузь область: `path` на подкаталог либо фильтр.
* **Листинг не заменяет `grep`:** `name_contains` ищет подстроку в имени файла, а не в его
  содержимом, и полноценный glob не поддерживает. Разведка по коду — это `plan_task`.

**Git.** `run_git(project_dir, operation, …)`: `status`, `log`, `diff`, `branch_list`,
`branch_create`, `checkout_branch`, `add_commit`.

* `project_dir` должен быть **корнем репозитория** — каталогом, в котором лежит `.git`.
  Подкаталог отклоняется.
* Сетевых и разрушительных операций (`push`, `pull`, `reset`, `rebase`, `merge`) там нет вовсе.
* **`success: false` — это не ошибка вызова.** `isError` там `false`, неудачу видно по полю
  `success`, а текст для пользователя лежит в `git_stderr`: покажи его, а не свою формулировку.
* **`add_commit` коммитит весь индекс**, а не только переданные `paths`. Что реально вошло —
  в поле `files` ответа. Перед коммитом посмотри `status` и согласуй с пользователем, что именно
  коммитится.

Для правок кода по-прежнему нужен полный протокол.

## Автоодобрение команд

Если в конфиге моста задан `autoApproveCommands`, перечисленные там команды `Bash` проходят без
одобрения оператора.

* **Совпадение точное, посимвольное, по всей строке целиком.** Пробелы по краям отбрасываются,
  внутренние — нет. Любое отличие в обёртке (другой `tail -N`, добавленный `echo $?`, другой
  пайп) делает строку новой и уводит её из списка, хотя смысл вызова не изменился.
* **Не импровизируй над обёрткой.** Канонические формы команд задаёт проект-цель; используй их
  дословно. Нужен кусок вывода — прогони каноническую команду целиком, а `grep`/`sed` сделай
  отдельным вызовом, не встраивай фильтр в первый.
* **Автоодобренный вызов не появляется в `permission_requests`** — решать по нему нечего.

Пример такого соглашения — `CLAUDE.md` в репозитории самого `ccc-mcp`. Учти: тот файл написан для
случая, когда Claude Code работает **над** этим репозиторием, а не использует его как мост.
Соглашение о канонических формах для твоего проекта ищи в его собственных инструкциях.

## Антипаттерны

Не делай:

* не вызывай `execute_task`, не дождавшись `approve_plan`;
* не теряй `session_id` между вызовами;
* не одобряй план с `has_open_questions: true`;
* не придумывай `request_id` и `plan_digest` — оба берутся из ответа сервера;
* не забывай переопросить `get_task_status` после `approve_permission_request`;
* не суди об успехе по `subtype` — только по `ok`;
* не гоняй чтение файла, листинг и коммит через `plan_task`/`execute_task`;
* не отменяй задачу при `tool_running` и `rate_limited`;
* не отчитывайся о стоимости, пока задача не завершилась;
* не импровизируй над обёрткой автоодобряемой команды;
* не путай `list_project_files` с поиском по содержимому.
