# Протокол и поля ответа

## Протокол: план → одобрение → выполнение

Выполнение без одобренного плана невозможно. `execute_task` требует `session_id`, и этот
`session_id` должен быть предварительно проведён через `plan_task` и `approve_plan` — запустить
задачу «с нуля», минуя план, нельзя.

```
plan_task  →  показать план человеку  →  approve_plan  →  execute_task
 planned                                    approved      executing → executed
```

| Состояние | Что значит | Что разрешено |
|---|---|---|
| `needs_clarification` | В плане есть открытые вопросы | только повторный `plan_task` |
| `planned` | План получен, не одобрен | `approve_plan`, повторный `plan_task` |
| `approved` | Одобрен явным вызовом | `execute_task` |
| `executing` | Выполнение идёт прямо сейчас | `get_task_status`, `cancel_task` |
| `executed` | План выполнен | только новый цикл с `plan_task` |

Три правила, которые стоит знать заранее:

* **Повторный `plan_task` сбрасывает одобрение** в `planned`. Иначе можно было бы одобрить один
  план, перепланировать сессию на другой и выполнить его без нового согласия. Вместе с планом
  меняется и `plan_digest` — старый перестаёт подходить.
* **Сбой выполнения одобрение не сжигает.** `executed` ставится только при `ok: true`; после
  таймаута, отмены или ошибки API сессия возвращается в `approved`, и попытку можно повторить,
  не проходя весь цикл заново.
* **Пока задача идёт, одобрение занято** (`executing`): параллельный `execute_task` по той же
  сессии будет отклонён.

Состояние сессий живёт в памяти сервера и не дольше `sessionRetentionMs` (по умолчанию сутки).
После перезапуска сервера одобрения теряются — цикл нужно пройти заново. Просроченное одобрение
всегда означает отказ, то есть промах в безопасную сторону.

### Открытые вопросы вместо тихих предположений

В headless-режиме (`claude -p`) интерактивный диалог не показывается: вызов `AskUserQuestion`
CLI резолвит пустым ответом, и Claude Code молча продолжает работу на собственных догадках —
причём в результате об этом нет ни следа. Для протокола это худший из возможных сценариев:
план одобряют, не зная, что внутри что-то угадано.

Поэтому мост **запрещает `AskUserQuestion`** (`--disallowedTools`) в обоих вызовах: инструмент
не просто отклоняется при обращении, а вообще отсутствует в списке доступных модели. Вместе с
этим передаётся системная инструкция: не хватает информации — не предполагай, а выпиши
недостающее разделом `## Открытые вопросы` прямо в тексте ответа.

Если такой раздел найден, `plan_task` возвращает `has_open_questions: true`, а сессия попадает
в состояние `needs_clarification`. Одобрить её нельзя: и `approve_plan`, и `execute_task`
ответят отказом. Единственный путь дальше — задать эти вопросы пользователю и вызвать
`plan_task` заново с уточнённой формулировкой.

Доставка вопросов пользователю — задача вызывающего агента, а не моста: сервер лишь помечает
план как неготовый и говорит об этом в `next_step`.

> **Почему инструкция требует самодостаточного последнего сообщения.** В поле `result` ответа
> CLI попадает только последнее сообщение модели. На живых прогонах без этого требования модель
> писала раздел с вопросами в промежуточном ходе, а в результат отдавала «ответ с открытыми
> вопросами уже выше» — и мост считал, что вопросов нет. Поэтому системный промпт отдельно
> требует изложить итог целиком и не ссылаться на сказанное ранее.

Учтите ещё одно: `--system-prompt-snapshot` в Claude Code по умолчанию включён, то есть
системный промпт фиксируется при первом запросе сессии и переиспользуется на всех `--resume`
дословно. Так как `execute_task` всегда продолжает сессию, фактически действует инструкция,
переданная в `plan_task`; своя инструкция для `execute_task` вступает в силу только после
компактизации диалога.

### Про `plan_digest`

`plan_task` возвращает `plan_digest` — короткий хеш текста плана. `approve_plan` требует его
вторым аргументом и отказывает при несовпадении. Это не даёт одобрить план вслепую или по
угаданному `session_id`: одобряющий обязан держать в руках именно тот план, который вернул
сервер. Агента, решившего одобрить план самостоятельно, механизм не остановит — барьер
процедурный, а не технический.

## Долгие задачи

`plan_task` и `execute_task` ждут результат не дольше `wait_seconds` (по умолчанию 20 с) —
MCP-клиент оборвал бы вызов раньше, чем закончится получасовая задача. Успели — полный отчёт
сразу; не успели — `status: "running"` и `process_id`:

```json
{ "process_id": "6f0c…", "status": "running",
  "next_step": "Задача выполняется. Опросите её: get_task_status с process_id \"6f0c…\"" }
```

Дальше опрашиваем. `wait_seconds` здесь означает «подожди до N секунд, если задача ещё идёт»:

```json
{ "name": "get_task_status", "arguments": { "process_id": "6f0c…", "wait_seconds": 30 } }
```

`wait_seconds: 0` в `execute_task` — сразу уйти в фон, не дожидаясь ничего.

### Почему вернулось ожидание

Ожидание кончается не только по времени. Поле `wait_ended_reason` говорит, чем именно:

| Значение | Что произошло | Что делать |
|---|---|---|
| `completed` | Задача закончилась | Читать `ok` и `result_text` — отчёт полный. |
| `timeout` | Вышло время `wait_seconds`, задача идёт | Опросить `get_task_status` ещё раз. |
| `pending_permission` | Досрочный выход: у моста изменился состав запросов, ждущих решения | Разобрать `permission_requests` немедленно. |
| `null` | Ожидания в этом вызове не было (`wait_seconds: 0` либо задача уже была завершена) | — |

`pending_permission` — отдельная причина, а не разновидность таймаута: иначе операция,
поднятая через секунду после старта, ждала бы весь `wait_seconds`, причём ещё до того, как у
вызывающего появится `process_id` для опроса. Просыпаться на любой прогресс задачи мост
намеренно не умеет: промежуточных событий у дочернего CLI десятки в секунду, и ожидание
выродилось бы в горячий опрос, потеряв смысл `wait_seconds` — «припарковаться и получить ответ».

## Поля ответа

| Поле | Смысл |
|---|---|
| `ok` | Задача действительно удалась. |
| `status` | `running` / `done` / `failed` / `timeout` / `canceled` |
| `session_id` | Для продолжения следующим вызовом. |
| `session_state` | Где сессия в протоколе: `needs_clarification` / `planned` / `approved` / `executing` / `executed`. |
| `plan_digest` | Отпечаток плана — его требует `approve_plan`. |
| `has_open_questions` | В плане есть раздел «Открытые вопросы» — одобрять нельзя. |
| `next_step` | Какой шаг протокола следующий. |
| `model_requested` | Что мост передал в `--model`. `null` — флаг не передавался, модель выбирал сам CLI. |
| `model_used` | Какая модель отработала на самом деле: алиас уже развёрнут (`opus` → `claude-opus-5`). Основная модель прогона — служебные вызовы дешёвой модели сюда не попадают, но целиком видны в `raw.modelUsage`. |
| `result_text` | План или итоговый отчёт Claude Code. |
| `hint` | Человеческая подсказка, если ошибка распознана. |
| `parse_error` | Заполняется, если JSON от CLI получить не удалось. |
| `raw` | Сырой JSON-ответ Claude Code целиком. |
| `permission_requests` | Операции, потребовавшие разрешения. Пустой массив, пока `hooksEnabled: false`. |
| `pending_permission_count` | Сколько из них ждут вашего решения прямо сейчас. |
| `progress` | Живое состояние задачи по потоку событий. Всегда объект, никогда `null` — см. ниже. |
| `wait_ended_reason` | Почему кончилось ожидание в этом вызове. |
| `total_cost_usd` | Итоговая стоимость. Пока задача идёт — `null`: считать её раньше времени нечем. |

**Почему нельзя смотреть только на `subtype`.** Claude Code отдаёт ошибки в таком виде:

```json
{"type":"result","subtype":"success","is_error":true,
 "result":"Not logged in · Please run /login","terminal_reason":"api_error"}
```

`subtype` здесь `"success"`, хотя это провал. Мост считает `ok` по связке
`is_error` + `exit_code` + `terminal_reason` — ориентируйтесь на `ok`.

## Живое состояние: `progress`

Пока задача идёт, `status: "running"` — единственное, что о ней известно снаружи. Объект
`progress` в каждом ответе превращает поток событий дочернего CLI в набор счётчиков: что
вызывалось, чем кончился последний вызов, не ходит ли модель по кругу, когда была последняя
активность.

**Форма не мигает: все ключи присутствуют всегда.** При `streamEvents: false`, ошибке спавна
или молчащем CLI это нули, пустые карты и `null` — но не отсутствующие поля и не `null` вместо
всего объекта. У завершённой задачи значения заморожены на моменте конца, а не растут дальше.

| Поле | Смысл |
|---|---|
| `streaming` | Пришла хотя бы одна строка потока. |
| `elapsed_ms` | Сколько задача идёт. У завершённой заморожено. |
| `last_activity_at` | ISO-время последнего события потока. |
| `idle_seconds` | Главный признак зависания — вместе с `open_tool_calls`. |
| `model` | Запрошенная модель из `system/init`. Не то же, что `model_used` отчёта. |
| `assistant_events` | Ходов ассистента. |
| `assistant_text_blocks` | Блоков видимого текста. |
| `tool_calls` | Вызовов инструментов. |
| `tool_results` | Пришедших результатов. |
| `tool_errors` | `tool_result` с `is_error` — в основном отказы моста разрешений. |
| `open_tool_calls` | Вызовы без результата: «инструмент ещё работает», а не «задача зависла». |
| `tools_used` | Карта «имя инструмента → сколько раз». |
| `last_tool_call` | Последний вызов целиком, либо `null`. |
| `last_assistant_text` | Последнее видимое сообщение модели, ≤600 символов. Рассуждения сюда не попадают по построению. |
| `thinking_blocks` | Блоков рассуждения. |
| `thinking_token_events` | Пульсов `system/thinking_tokens`. |
| `estimated_thinking_tokens` | Оценка самого CLI, не наш расчёт по токенам. |
| `cache_read_input_tokens` | Прочитано из кеша промпта. |
| `cache_creation_input_tokens` | Записано в кеш промпта. |
| `rate_limit` | Состояние лимита использования, либо `null`. |
| `recent_events` | Кольцо последних 20 событий. |
| `last_result_cost_usd` | Стоимость по последней строке `result` — см. ниже. |
| `bad_lines` | Строк потока, которые не удалось разобрать. |
| `oversize_lines` | Строк сверх предела длины. |
| `unknown_event_types` | Карта «незнакомый тип события → сколько раз». |

`last_tool_call`:

| Поле | Смысл |
|---|---|
| `name` | Имя инструмента дочернего CLI. |
| `summary` | Выжимка ввода — та же, что видит оператор в запросе на разрешение. Сырой `tool_input` наружу не идёт. |
| `request_id` | Совпадает с `request_id` в `permission_requests`: именно его одобряет оператор. |
| `at` | ISO-время вызова. |
| `completed` | Пришёл ли `tool_result`. Отказ хука — тоже пришёл. |
| `is_error` | `is_error` результата. `null` — результата ещё не было. |
| `repeat` | Какой по счёту это вызов с теми же аргументами (`1` — первый). |

`rate_limit`: `status`, `utilization` (доля выработки пятичасового окна, `0…1`), `resets_at`
(ISO). `recent_events[]`: `at`, `kind`, `text`.

**Чего в `progress` нет намеренно.** Снимок внутри моста знает больше, но наружу идёт только
то, по чему вызывающий агент способен принять решение:

* `startedAt`/`finishedAt` — их уже несут `elapsed_ms` и `duration_ms` отчёта;
* `segments`/`resultEvents` — механика сегментов внутри одного процесса CLI, действовать по
  ней нельзя (см. [internals.md](internals.md));
* `repeatedCalls` — карта непрозрачных отпечатков. Сам факт хождения по кругу выдаётся
  паттерном `repeated_tool_call` человеческой фразой в `next_step`, а сырая карта заставляла бы
  вызывающего считать пороги самостоятельно.

**`last_result_cost_usd` — не итоговая стоимость.** Это `total_cost_usd` последней встреченной
строки `result`: точное накопительное число CLI, а не оценка по токенам. `null` означает «ни
один сегмент ещё не завершился» и не равно нулю. Итог задачи — по-прежнему `total_cost_usd`
отчёта, известный только по завершении.

Что означает каждый паттерн в `next_step` и по каким порогам он срабатывает —
в [internals.md](internals.md).

## `session_id`: откуда он берётся

Кандидаты по убыванию достоверности:

1. `session_id` из разобранной строки `result` — итоговый отчёт CLI;
2. `session_id` из строки `system/init` потока;
3. `session_id`, переданный на вход вызова.

Второй кандидат — самое полезное здесь. Строка `init` приходит примерно через секунду после
спавна, а не в конце прогона, поэтому **отменённая и отвалившаяся по таймауту задача остаётся
возобновляемой**: итогового отчёта у неё нет, а идентификатор есть.

## Что остаётся после `cancel_task`

Итоговый отчёт CLI мост не подделывает: `result_text` у остановленной задачи остаётся `null` —
из него выводятся `plan_digest` и `has_open_questions`, а частичный результат планом одобрить
нельзя. Но пустоты тоже не остаётся.

* **`hint`** вместо формально верного «процесс был остановлен, поэтому JSON-отчёт не
  сформирован» перечисляет, что успело произойти: длительность, число вызовов инструментов и
  три самых частых имени, последний вызов и завершился ли он, число ходов ассистента,
  последнее видимое сообщение модели (срез 160 символов).
* **`progress.recent_events`, `tools_used`, `last_tool_call`** — подробности.
* **`session_id` сохранён** — ту же сессию можно продолжить новым циклом
  `plan_task` → `approve_plan` → `execute_task`, передав его на вход.

Два особых случая. Если убийство догнало нормальное завершение, отчёт CLI всё же успел прийти —
`hint` так и говорит, и смотреть надо `result_text`. Если поток был выключен
(`streamEvents: false`) или дочерний CLI не выдал ни одной строки, живого состояния нет вовсе —
судить о сделанном нечем, остаётся stderr в логе.
