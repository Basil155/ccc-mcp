# Пооперационные разрешения (PreToolUse-хуки)

> **Статус: по умолчанию выключено (`hooksEnabled: false`).**
> Основной путь — удержание вызова до решения оператора — от поведения модели не зависит. Запасной
> путь (отказ после истёкшего удержания) держится на том, что модель повторит вызов, а это зависит
> от версии CLI и после его обновления стоит перепроверить.
> Проверено вручную: Windows 11, Claude Code 2.1.274 — вызов, одобренный во время удержания,
> проходит с первой попытки без повторов (`denied_count: 0`), а `allow` хука перекрывает
> собственный отказ CLI «requires approval» в headless-режиме.

Одобрение плана даётся авансом за весь прогон: после старта `execute_task` мост не контролирует
отдельные операции. `hooksEnabled: true` добавляет второй контур. При запуске задачи мост
поднимает HTTP-сервер на `127.0.0.1` со случайным портом и передаёт дочернему CLI
`--settings` с PreToolUse-хуком на каждый инструмент из `sensitiveTools`.

Как это выглядит по шагам:

1. Дочерний Claude Code хочет выполнить `Bash`, `Write` или `Edit`.
2. Мост **не отвечает сразу, а держит HTTP-запрос хука** до `permissionHoldSeconds`
   (по умолчанию 120 с). Дочерний CLI всё это время просто ждёт ответа.
3. Запрос появляется в `permission_requests` ответа `get_task_status` со статусом `pending`.
4. Вы показываете его пользователю и вызываете `approve_permission_request`.
5. Мост тут же отвечает удержанному вызову `allow` (или `deny`), и операция проходит **с первой
   попытки** — модели не нужно ни ждать, ни повторять вызов.

Если за время удержания решения нет, мост отвечает отказом с просьбой подождать и повторить ровно
тот же вызов, и повтор удерживается снова. Это запасной путь, и на него нельзя полагаться
всерьёз: модель вправе не поверить тексту отказа, счесть его посторонней инструкцией и сдаться.
Так и было при проверке на Windows до появления удержания: пять попыток за 10 секунд, и
оркестратор не успевал ответить. `permissionHoldSeconds: 0` возвращает прежнее поведение — отказ
сразу.

**Таймаут хука выставляется явно** — удержание плюс 60 секунд. Это не косметика: истёкший таймаут
HTTP-хука (как и обрыв соединения) Claude Code трактует как non-blocking error и **пропускает**
вызов. Мост поэтому всегда отвечает сам и заметно раньше, чем CLI сдастся.

```json
{ "name": "approve_permission_request",
  "arguments": { "process_id": "6f0c…", "request_id": "a1b2c3d4e5f6",
                 "decision": "allow", "reason": "тесты запускать можно" } }
```

Поля записи в `permission_requests`:

| Поле | Смысл |
|---|---|
| `request_id` | Отпечаток вызова: `sha256(tool_name + канонизированный tool_input)`, 12 hex. |
| `tool_name` | Инструмент дочернего CLI. |
| `summary` | Выжимка аргументов для показа человеку. Сырой `tool_input` наружу не отдаётся. |
| `decision` | `pending` / `approved` / `denied` / `exhausted`. |
| `denied_count` | Сколько раз хук ответил отказом: по нему видно, повторяет ли модель вызов. Попытка, одобренная во время удержания, отказом не считается, так что одобренный с первого раза вызов показывает `0`. |
| `allowed_count` | Сколько раз вызов прошёл после одобрения. |

Что стоит знать до включения:

* **`request_id` нельзя угадать.** Это дайджест самого вызова — то же свойство, что у
  `plan_digest` в `approve_plan`: одобрить вслепую не получится.
* **Одобрение привязано к точным аргументам.** Если при повторе модель изменит хоть байт
  значимых аргументов, получится новый запрос с новым `request_id`. Свободный `description`
  у `Bash` из ключа исключён, потому что модель перефразирует его почти наверняка.
* **Одобрение «липкое» в пределах задачи**, а не одноразовое: хук может сработать по одному
  ключу больше раза. Отозвать — повторный вызов с `decision: "deny"`.
* **Бюджет повторов — fail-closed.** В бюджет идут попытки, закончившиеся отказом. Удержанная
  попытка засчитывается, только если удержание истекло без решения, поэтому при удержании в 120 с
  десять попыток — это до 20 минут ожидания. После `retryBudget` отказов запрос переходит в
  `exhausted` и запрещается до конца задачи. Разрешения нельзя «продавить», продолжая
  пытаться. Оператор при этом всё ещё может одобрить исчерпанный запрос.
* **Синхронная пауза `sleep N` (N ≤ 60) проходит без одобрения** — чтобы модель могла дождаться
  решения, не сжигая бюджет мгновенными ретраями. Та же команда с `run_in_background: true`
  одобрения требует: фоновый `Bash` возвращается мгновенно и ждать модель не заставляет, то есть
  не делает того, ради чего исключение существует. Рассчитывать на паузу всё равно нельзя:
  харнесс дочернего CLI может запретить `sleep` в `Bash` раньше моста (так ведёт себя Claude Code
  standalone), и вызов до моста просто не дойдёт. Поэтому подсказка в отказе велит подождать
  **любым** способом, не называя команды, а реальное время до исчерпания `retryBudget` зависит
  от того, как именно модель ждёт: ориентируйтесь на число попыток, а не на минуты. Отключается
  `allowWaitCommand: false`.
* **Хуки ставятся и на `plan_task`,** но со своим набором: `Bash` и `Monitor` независимо от
  `sensitiveTools` и со своим списком `planAutoApproveCommands`. Подробности — в разделе
  [Планирование](#планирование).
* **`sensitiveTools` по умолчанию `["Bash", "Write", "Edit"]`** даёт максимальный контроль,
  но при `permission_mode: "acceptEdits"` превращает каждую правку файла в отдельное
  одобрение. Для реальных задач практичнее оставить только `["Bash"]`.
* **Отказ хука сильнее правил `permissions.allow`** в настройках Claude Code. Команда,
  разрешённая в `~/.claude/settings.json`, при включённых хуках всё равно уйдёт оператору,
  если её нет в `autoApproveCommands`. Частые безопасные команды приходится держать в обоих
  местах: `permissions.allow` покрывает запуски без хуков, `autoApproveCommands` —
  `execute_task`, `planAutoApproveCommands` — `plan_task`.
* **Inline JSON в `--settings` виден в `ps`** другим локальным пользователям. Утечёт только
  URL моста: одобрять через него нельзя (это умеет лишь MCP-тул), максимум — исчерпать
  чужой `retryBudget`. Для однопользовательской машины приемлемо.

## Планирование

Режим плана Claude Code (`--permission-mode plan`) — не песочница. Он запрещает правку файлов
(кроме собственного файла плана), но Bash-команды проверяет по обычным правилам разрешений:
всё, что пропускают `permissions.allow` пользователя или проекта (`Bash(python3 *)`,
`Bash(docker compose *)`…), выполняется и в планировании. 23.09 так в `plan_task` прошли
`docker compose down`/`up --build`, запись в redis, живые сценарии и перезапись двух файлов
через `python3 -c`.

Что мост делает с этим:

* **Отключает auto-режим в планировании.** По умолчанию CLI в режиме плана включает
  классификатор auto-режима, если тот доступен модели (`useAutoModeDuringPlan: true`), и тот
  сам одобряет команды, в том числе пишущие. Для opus он доступен, для haiku нет: на opus
  `plan_task` выполнил непрозрачный скрипт, пишущий файл, а на haiku та же команда получила
  «This command requires approval». Мост передаёт `useAutoModeDuringPlan: false` в
  `--settings` каждого `plan_task`, независимо от `hooksEnabled`.
* **При `hooksEnabled: true` ставит хук и на `plan_task`** — на `Bash` и `Monitor` (оба
  исполняют произвольный shell), независимо от `sensitiveTools`. Команды, которые только
  читают, мост пропускает сам (`planAutoApproveReadOnly`, по умолчанию `true`); остальные,
  кроме точного списка `planAutoApproveCommands`, ждут решения оператора. Список отдельный,
  потому что годное для выполнения (`npm run build` пишет `dist/`) не обязательно годится для
  плана.
* **Объясняет границу модели** в системном промпте планирования: менять ничего нельзя, даже
  если разрешения пропустили бы, а задачу «выполни» надо превратить в план.

Без `hooksEnabled` остаётся дыра через `permissions.allow`: команды, подпадающие под эти
правила, в планировании выполняются без вопросов. Закрывает её только хук.

### Автоодобрение читающих команд (`planAutoApproveReadOnly`, `executeAutoApproveReadOnly`)

Строгий режим «каждая команда к оператору» на практике не работал: 24.09 восемь `plan_task` по
одному проекту дали около 130 ручных одобрений, почти все на `grep`, `ls`, `find`,
`docker ps/logs`, `sed -n`, и один прогон упёрся в `maxPendingRequests`. Точный список не
помогал: дословно модель повторила одну команду из 142. Поэтому мост сам разбирает команду
(с учётом кавычек, по словам, а не регулярками по строке) и пропускает её, если она только
читает. Классификатор консервативен: `false` значит «не уверен», и команда идёт к оператору,
как раньше. На командах разведки того дня он пропустил 92 из 104; оставшиеся 12 и должны были
уйти к оператору.

Пропускается, если **каждое** звено цепочки (`|`, `&&`, `||`, `;`) — из белого списка:
`cat`, `head`, `tail`, `wc`, `ls`, `grep`, `cut`, `tr`, `echo`, `stat`, `du`, `strings`,
`jq`, `diff`, `cd`, `ps`, `pgrep` и подобные; `find` без `-exec`/`-delete`/`-fprint`;
`sed` только как `sed -n 'A,Bp'`; `awk` без `>`, `|`, `system`, `getline`; `sort` без `-o`;
`xargs` только с простыми читателями; `git` — `log`, `show`, `status`, `diff`, `blame`,
`grep`, `ls-files`, `rev-parse` и список веток/тегов, без `-c` и `--output`; `docker` — `ps`,
`logs`, `inspect`, `images`, `compose ps/logs/config`; `dotnet --info/--list-sdks`.

Всегда идёт к оператору:

* интерпретаторы и скрипты (`python3`, `node`, `sh`, `./script`, `.venv/bin/python`), сеть
  (`curl`), `docker exec`, `docker compose up/down`, сборки и тесты;
* перенаправление куда-либо кроме `/dev/null`, `tee`, `sed -i`;
* подстановки команд (`$(…)`, обратные кавычки, `<(…)`), heredoc, фон (`&`), подоболочки,
  циклы и условия;
* присваивание перед командой (`GIT_EXTERNAL_DIFF=… git diff`, `LD_PRELOAD=… cat`);
* аргументы, похожие на путь к секретам: `.env`, `*.pem`, `*.key`, `credentials`,
  `secrets/`, `~/.ssh`, `~/.aws` — чтение секретов оператор должен видеть. Шаблоны без значений
  (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`) секретами не считаются, если
  не лежат в каталоге секретов.

Ограничение: секреты распознаются по явному пути в аргументах. Глоб (`cat infra/*`) или
рекурсивный `grep` по домашнему каталогу прочитают и секреты, не попав к оператору. Граница
автоодобрения — «не меняет состояние», а не «не читает ничего чувствительного».

В логе такие вызовы — `decision: "auto_allowed"` с `rule: "read_only"`. `false` возвращает
строгий режим.

Тот же классификатор работает и в `execute_task` (`executeAutoApproveReadOnly`, по умолчанию
`true`): одобрение плана уже дано, а читающая команда ничего не меняет. 26.09 `execute_task`
упёрся в часовой таймаут, потратив его на 42 ручных одобрения; последние четыре ждавших
решения были `grep`. Пишущее при выполнении по-прежнему идёт к оператору, если его нет в
`autoApproveCommands`.

## Оператор не на связи (`operatorAbsentMinutes`)

Решения по запросам принимает оркестратор, опрашивающий `get_task_status`. Если он пропал —
оборвалась связь, закончилась его сессия, — запросы висят, модель раз за разом ждёт и повторяет,
а задача доживает до `timeoutMs` и кончается без отчёта. 24.09 так прошли 70 минут
`execute_task`: с 08:44 два запроса ждали решения, которое некому было принять.

Мост отмечает, когда оператор последний раз обращался к задаче: запуск, `get_task_status` (до и
после ожидания), `approve_permission_request`, `cancel_task`, `list_tasks`. Если молчание
дольше `operatorAbsentMinutes` (по умолчанию 10), запросы, которые ждали бы человека, получают
**окончательный отказ** с текстом: оператор не выходит на связь N минут, ждать и повторять не
нужно, продолжи без операции и перечисли несделанное в итоговом отчёте. Уже одобренные запросы
и автоодобрение продолжают работать. Такие записи видны в `permission_requests` с
`decision: "denied"` и `operator_absent: true`, в логе — с `operator_absent: true`.

Следствие для оркестратора: опрашивайте идущую задачу чаще, чем раз в `operatorAbsentMinutes`
(обычный опрос с `wait_seconds` до 120 с это и так обеспечивает). Если вы ждёте ответа
пользователя дольше, запросы этой задачи будут отклонены, и решение придётся принимать уже по
отчёту. `0` отключает механизм: мост ждёт решения до таймаута задачи, как раньше.

## Автоодобрение команд (`autoApproveCommands`)

Список команд `Bash`, которые мост пропускает без одобрения оператора — чтобы десятки одинаковых
`npm run typecheck` за прогон не превращались в десятки одинаковых нажатий «да», которые ничего
не проверяют.

* **Совпадение точное, посимвольное, по всей строке целиком.** Лишние пробелы по краям
  отбрасываются, внутренние — нет. Ни префиксов, ни шаблонов, ни регулярных выражений:
  `npm run typecheck && rm -rf /` и `npm run typecheck --watch` идут обычным путём наравне
  с любой незнакомой командой.
* **Список пуст по умолчанию** и действует только на `Bash`: у `Write`/`Edit` единственной
  строки-команды попросту нет. Незнакомое поле в `tool_input` отменяет автоодобрение — вызов
  уходит оператору.
* **Фоновый вызов автоодобряется наравне с обычным**, в отличие от паузы: `sleep` в фоне теряет
  весь свой смысл, а сборка — нет.
* **Автоодобренный вызов не появляется в `permission_requests`** ни на секунду: решать нечего,
  и дочерний процесс не ждёт. Единственный его след — строка лога с `"decision": "auto_allowed"`.
* Задаётся в конфиге либо переменной `CCC_AUTO_APPROVE_COMMANDS` (команды через `;`).

Что класть в список, решаете вы: **мост семантику команд не проверяет.** Разумное правило —
только детерминированные проверки, не тратящие деньги и не ходящие в сеть.

### Что сюда не кладут

* **`sleep` с `run_in_background: true`.** Это работа `allowWaitCommand`, и фоновый вариант
  исключён там намеренно — см. список выше.
* **`npm run smoke` без `--no-live`.** Порождает дочерние процессы `claude`, то есть тратит
  деньги пользователя. Каждый такой прогон должен стоить явного разрешения.
* **Пишущий git** (`git commit`, `git push` и всё, что меняет состояние репозитория). Для этого
  есть `run_git` — он работает вне протокола хуков вовсе, не требует одобрения и не тратит
  `retryBudget`; см. [tools.md](tools.md).

### Канонические формы задаёт проект-цель

Раз совпадение посимвольное, любое отличие в обёртке — другой `tail -N`, добавленный
`echo $?`, другой пайп — превращает команду в новую строку, которая под список уже не подпадает,
хотя смысл вызова не изменился. Значит, в проекте должно существовать соглашение о том, как
именно эти команды пишутся, и агент должен его знать.

Рабочий образец такого соглашения — [`CLAUDE.md`](../CLAUDE.md) этого репозитория: три команды
в фиксированной форме плюс правило «нужен кусок вывода — прогони каноническую команду целиком,
а `grep` сделай отдельным вызовом, не встраивай фильтр в первый».
