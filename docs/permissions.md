# Пооперационные разрешения (PreToolUse-хуки)

> **Статус: экспериментально, по умолчанию выключено (`hooksEnabled: false`).**
> Механизм держится на том, что дочерний Claude Code реально повторит отклонённый вызов после
> одобрения. Это поведение зависит от версии CLI и требует ручной проверки — см. ниже.

Одобрение плана даётся авансом за весь прогон: после старта `execute_task` мост не контролирует
отдельные операции. `hooksEnabled: true` добавляет второй контур. При запуске задачи мост
поднимает HTTP-сервер на `127.0.0.1` со случайным портом и передаёт дочернему CLI
`--settings` с PreToolUse-хуком на каждый инструмент из `sensitiveTools`.

Как это выглядит по шагам:

1. Дочерний Claude Code хочет выполнить `Bash`, `Write` или `Edit`.
2. Мост **мгновенно отвечает отказом** с инструкцией: не искать обходной путь, подождать и
   повторить ровно тот же вызов. Ждать человека хендлер не может — это упёрлось бы в таймаут
   хука на стороне CLI, поэтому ответ всегда немедленный.
3. Запрос появляется в `permission_requests` ответа `get_task_status` со статусом `pending`.
4. Вы показываете его пользователю и вызываете `approve_permission_request`.
5. Дочерний процесс повторяет вызов, и на этот раз мост пропускает его.

```json
{ "name": "approve_permission_request",
  "arguments": { "process_id": "6f0c…", "request_id": "a1b2c3d4e5f6",
                 "decision": "allow", "reason": "тесты запускать можно" } }
```

Поля записи в `permission_requests`:

| Поле | Смысл |
|---|---|
| `request_id` | Отпечаток вызова: `sha256(tool_name + канонизированный tool_input)`, 12 hex. |
| `tool_name` | Инструмент дочернего CLI. |
| `summary` | Выжимка аргументов для показа человеку. Сырой `tool_input` наружу не отдаётся. |
| `decision` | `pending` / `approved` / `denied` / `exhausted`. |
| `denied_count` | Сколько раз модель уже пыталась — по нему видно, повторяет ли она вызов. |
| `allowed_count` | Сколько раз вызов прошёл после одобрения. |

Что стоит знать до включения:

* **`request_id` нельзя угадать.** Это дайджест самого вызова — то же свойство, что у
  `plan_digest` в `approve_plan`: одобрить вслепую не получится.
* **Одобрение привязано к точным аргументам.** Если при повторе модель изменит хоть байт
  значимых аргументов, получится новый запрос с новым `request_id`. Свободный `description`
  у `Bash` из ключа исключён, потому что модель перефразирует его почти наверняка.
* **Одобрение «липкое» в пределах задачи**, а не одноразовое: хук может сработать по одному
  ключу больше раза. Отозвать — повторный вызов с `decision: "deny"`.
* **Бюджет повторов — fail-closed.** После `retryBudget` отказов запрос переходит в
  `exhausted` и запрещается до конца задачи. Разрешения нельзя «продавить», продолжая
  пытаться. Оператор при этом всё ещё может одобрить исчерпанный запрос.
* **Синхронная пауза `sleep N` (N ≤ 60) проходит без одобрения** — чтобы модель могла дождаться
  решения, не сжигая бюджет мгновенными ретраями. Та же команда с `run_in_background: true`
  одобрения требует: фоновый `Bash` возвращается мгновенно и ждать модель не заставляет, то есть
  не делает того, ради чего исключение существует. Рассчитывать на паузу всё равно нельзя:
  харнесс дочернего CLI может запретить `sleep` в `Bash` раньше моста (так ведёт себя Claude Code
  standalone), и вызов до моста просто не дойдёт. Поэтому подсказка в отказе велит подождать
  **любым** способом, не называя команды, а реальное время до исчерпания `retryBudget` зависит
  от того, как именно модель ждёт: ориентируйтесь на число попыток, а не на минуты. Отключается
  `allowWaitCommand: false`.
* **Хуки ставятся только на `execute_task`.** В режиме планирования модель не меняет файлы,
  а `Bash` нужен ей для разведки.
* **`sensitiveTools` по умолчанию `["Bash", "Write", "Edit"]`** даёт максимальный контроль,
  но при `permission_mode: "acceptEdits"` превращает каждую правку файла в отдельное
  одобрение. Для реальных задач практичнее оставить только `["Bash"]`.
* **Windows не проверялся.** Риск низкий: HTTP-запрос делает сам CLI своим кодом, ни shell,
  ни `cmd` в цепочке не участвуют — в отличие от command-хуков. Но до проверки держите
  `hooksEnabled: false`.
* **Inline JSON в `--settings` виден в `ps`** другим локальным пользователям. Утечёт только
  URL моста: одобрять через него нельзя (это умеет лишь MCP-тул), максимум — исчерпать
  чужой `retryBudget`. Для однопользовательской машины приемлемо.

## Автоодобрение команд (`autoApproveCommands`)

Список команд `Bash`, которые мост пропускает без одобрения оператора — чтобы десятки одинаковых
`npm run typecheck` за прогон не превращались в десятки одинаковых нажатий «да», которые ничего
не проверяют.

* **Совпадение точное, посимвольное, по всей строке целиком.** Лишние пробелы по краям
  отбрасываются, внутренние — нет. Ни префиксов, ни шаблонов, ни регулярных выражений:
  `npm run typecheck && rm -rf /` и `npm run typecheck --watch` идут обычным путём наравне
  с любой незнакомой командой.
* **Список пуст по умолчанию** и действует только на `Bash`: у `Write`/`Edit` единственной
  строки-команды попросту нет. Незнакомое поле в `tool_input` отменяет автоодобрение — вызов
  уходит оператору.
* **Фоновый вызов автоодобряется наравне с обычным**, в отличие от паузы: `sleep` в фоне теряет
  весь свой смысл, а сборка — нет.
* **Автоодобренный вызов не появляется в `permission_requests`** ни на секунду: решать нечего,
  и дочерний процесс не ждёт. Единственный его след — строка лога с `"decision": "auto_allowed"`.
* Задаётся в конфиге либо переменной `CCC_AUTO_APPROVE_COMMANDS` (команды через `;`).

Что класть в список, решаете вы: **мост семантику команд не проверяет.** Разумное правило —
только детерминированные проверки, не тратящие деньги и не ходящие в сеть.

### Что сюда не кладут

* **`sleep` с `run_in_background: true`.** Это работа `allowWaitCommand`, и фоновый вариант
  исключён там намеренно — см. список выше.
* **`npm run smoke` без `--no-live`.** Порождает дочерние процессы `claude`, то есть тратит
  деньги пользователя. Каждый такой прогон должен стоить явного разрешения.
* **Пишущий git** (`git commit`, `git push` и всё, что меняет состояние репозитория). Для этого
  есть `run_git` — он работает вне протокола хуков вовсе, не требует одобрения и не тратит
  `retryBudget`; см. [tools.md](tools.md).

### Канонические формы задаёт проект-цель

Раз совпадение посимвольное, любое отличие в обёртке — другой `tail -N`, добавленный
`echo $?`, другой пайп — превращает команду в новую строку, которая под список уже не подпадает,
хотя смысл вызова не изменился. Значит, в проекте должно существовать соглашение о том, как
именно эти команды пишутся, и агент должен его знать.

Рабочий образец такого соглашения — [`CLAUDE.md`](../CLAUDE.md) этого репозитория: три команды
в фиксированной форме плюс правило «нужен кусок вывода — прогони каноническую команду целиком,
а `grep` сделай отдельным вызовом, не встраивай фильтр в первый».
