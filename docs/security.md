# Безопасность

* **Правка файлов силами Claude Code — только по одобренному плану.** `execute_task` не умеет
  стартовать без `session_id` и отказывает, пока сессия не проведена через `plan_task` и
  `approve_plan`. Одобрение привязано к конкретному плану (`plan_digest`) и конкретному каталогу,
  расходуется при успешном выполнении и сбрасывается при перепланировании.
* **`plan_task` не песочница.** Правку файлов режим плана запрещает, а Bash — нет: команды,
  которые пропускают правила `permissions.allow`, выполняются и в планировании. Мост отключает
  в планировании auto-режим CLI, а при `hooksEnabled` ставит хук и на `plan_task`, и тогда
  каждая команда ждёт оператора. Без `hooksEnabled` граница держится только на правилах
  разрешений и на системном промпте. Подробности — в
  [permissions.md](permissions.md#планирование).
* **`write_project_file` — сознательное исключение из этого правила.** Он перезаписывает один
  текстовый файл внутри `allowedRoots` напрямую, без плана и без одобрения. Списка разрешённых
  имён файлов у него нет намеренно: тот же результат и так достижим через обычный цикл
  `plan_task` → `approve_plan` → `execute_task`, поэтому сужение не давало бы реальной защиты,
  только неудобство. Единственная граница — белый список каталогов, ровно та же, что у остальных
  инструментов. Каждая такая запись попадает в лог с `sha256` до и после, так что по логу видно,
  какой файл и какой именно версией был перезаписан.
* **`list_project_files` только читает** и границей `project_dir` не торгует: он никогда не
  заходит внутрь символических ссылок, поэтому ссылка наружу не превращает листинг в способ
  посмотреть чужой каталог, а симлинк-петля — в бесконечный обход.
* **`run_git` — не «git с произвольными аргументами».** Действие выбирается перечислением из семи
  вариантов, каждый со своим набором типизированных параметров. Ни `push`, ни `reset`, ни
  `--force` в схеме не существуют, поэтому и блокировать их нечем: попытка передать такую операцию
  отсеивается обычной валидацией, а не отдельной проверкой безопасности, которую можно забыть.
  При этом `add_commit`, `branch_create` и `checkout_branch` меняют состояние репозитория **без
  плана и одобрения** — сознательно, по той же логике, что и `write_project_file` выше. Каждая
  операция попадает в лог.
* **`run_git` работает только в корне репозитория внутри `allowedRoots`.** Каталог обязан сам
  содержать `.git`; подкаталог отклоняется. Иначе git поднялся бы по дереву вверх и начал работать
  с репозиторием за пределами белого списка. Тем же закрыт и обход через окружение: переменные
  `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` и родственные им вычищаются перед запуском, потому
  что каждая из них уводит git от `cwd` к чужому репозиторию.
* **Подмена аргумента флагом закрыта раздельно.** Пути всегда идут после разделителя `--` (поэтому
  файл, реально названный `-rf.txt`, коммитится штатно), а имена веток проверяются allowlist'ом:
  латиница, цифры, точка, дефис, подчёркивание и слэш, первый символ — буквенно-цифровой. Имя вида
  `--upload-pack=…` отсекается именно этим правилом, поскольку прикрыть позиционный аргумент
  ветки разделителем `--` в git нельзя.
* **Никаких тихих предположений.** `AskUserQuestion` запрещён, а нехватка информации обязана
  выражаться разделом «Открытые вопросы», который блокирует одобрение плана.
* **Ключ родителя не передаётся.** Перед запуском `claude` из окружения вычищаются все
  переменные `ANTHROPIC_*` и `CLAUDE_*`. Это не только требование «не хранить токен», но и
  условие работоспособности: Claude Desktop экспортирует свой `ANTHROPIC_API_KEY`, и
  унаследовавший его дочерний процесс падает с `401 Invalid API key`. Если какая-то переменная
  всё же нужна — добавьте её имя в `passEnv`.
* **Мост не работает внутри своего же дочернего claude.** Дочерний Claude Code поднимает свои
  MCP-серверы, и при регистрации ccc-mcp в пользовательском scope среди них оказался бы и сам мост.
  Это дало бы дочернему процессу `plan_task`/`execute_task` — запуск следующих claude и одобрение
  собственных планов, — а также `run_git` и `write_project_file`, работающие мимо хуков разрешений.
  Поэтому окружение дочернего claude помечается `CCC_MCP_NESTED=1`, и сервер, увидевший эту
  метку, завершается на старте, не зарегистрировав ни одного инструмента. Метка не входит в
  вычищаемые `ANTHROPIC_*`/`CLAUDE_*` и доходит до всех потомков.
* **Без shell.** Процессы запускаются через `spawn` с `shell: false`, текст задачи уходит
  отдельным элементом argv — кавычки и `&&` внутри задачи безвредны. Так же и git: аргументы
  передаются массивом, а сообщение коммита — вообще через stdin, то есть не является элементом argv.
  Обёртки `.cmd`/`.bat` сервер отклоняет: они потребовали бы shell.
* **Белый список каталогов** проверяется до запуска процесса.
* **Таймаут** (`timeoutMs`, по умолчанию 30 минут) снимает зависший процесс вместе с
  потомками — на Windows через `taskkill /T /F`, поскольку обычный `kill` не трогает внуков.
* **`maxConcurrent`** не даёт расплодить процессы.
* **Пооперационные разрешения** (опционально, см. ниже) добавляют контроль внутри уже
  одобренного прогона: каждый запуск команды и запись в файл можно подтверждать отдельно.
