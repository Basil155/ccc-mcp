# Логирование

Каждый вызов пишется в JSONL (`logFile`): парные записи `start` / `finish` (или `timeout`,
`cancel`, `error`) с временем, каталогом, `session_id`, состоянием сессии, режимом разрешений,
началом текста задачи, кодом возврата, длительностью и стоимостью.

Шаги согласования тоже попадают в лог: `approve` — кто и какой план одобрил, `denied` — отказ
в выполнении с причиной. По логу восстанавливается вся цепочка «план → одобрение → выполнение».

При включённом контроле разрешений добавляются ещё два события: `hook` — каждое решение моста
по конкретной операции дочернего CLI (с `request_id`, инструментом, выжимкой аргументов и числом
попыток) и `permission` — решение оператора. Сырые `tool_input` в лог не пишутся, только
обрезанная выжимка.

Решения моста различаются полем `decision` записи `hook`: `approved` — вызов прошёл по
одобрению человека, `auto_allowed` — по совпадению с `autoApproveCommands`, то есть человека
никто не спрашивал. По логу видно и то, и другое; в `permission_requests` автоодобренные
вызовы не попадают вовсе.

Тело отчёта не пишется, пока не включите `logResultText: true`. Перед записью строки проходят
через редактор, вырезающий токены (`sk-ant-…`, пары вида `token: …`) и значения секретных
переменных окружения.

## Счётчики потока событий

Записи `finish`, `timeout` и `cancel` обогащены сводкой живого состояния **всегда, без всякого
флага**: несколько ключей в одной строке на задачу, и именно они делают видимым между
прогонами, металась ли модель по инструментам. Ключи: `stream_active`, `stream_session_id`,
`stream_assistant_events`, `stream_tool_calls`, `stream_tool_results`, `stream_tool_errors`,
`stream_open_tool_calls`, `stream_tools_used`, `stream_idle_seconds`, `stream_bad_lines`,
`stream_oversize_lines`, `stream_unknown_types`.

Снимок берётся на момент завершения, поэтому `stream_idle_seconds` в записи означает простой на
момент конца, а не время, прошедшее с тех пор. У `cancel` эта сводка и есть единственное
объяснение, что именно потеряно; там же `stream_session_id`, по которому прогон ещё можно
продолжить.

### Событие `progress`

Периодическая сводка того же состава по идущей задаче — плюс `process_id`, `tool`, `elapsed_ms`
и `pending_permissions`. Пишется под флагом `logProgress` (по умолчанию `false`) и не чаще
`logProgressIntervalMs` (по умолчанию 60 000 мс) на задачу.

Это телеметрия, а не аудит. Логируется не событие, а состояние по времени: событий у дочернего
CLI десятки в секунду, а так для 40-минутного прогона выходит ~40 строк. Таймера нет намеренно —
его пришлось бы создавать и гасить на четырёх путях завершения, а без него запись затихает
вместе с потоком, и молчание в логе само по себе информативно.

### Событие `stream_warn`

Разбор потока пошёл не так. Три класса, они же значения поля `reason`:

| `reason` | Что случилось |
|---|---|
| `unparseable` | Строка не разобралась как JSON-объект — вероятнее всего, дрейф формата. |
| `too_long` | Строка сверх предела длины (гигантский `tool_result`). |
| `no_result_line` | Процесс закончился, а итоговой строки `result` не было. |

Счётчики `bad_lines` живут в отчёте одной задачи, а здесь дрейф виден по всему логу. **Не чаще
одной записи на класс сбоя на процесс**: при полностью сломанном формате плохих строк бывают
сотни в секунду. Дублировать количество не нужно — его несёт `progress.bad_lines`. Ограничение
именно по классу, а не по процессу, потому что «непарсящаяся строка» и «строка сверх предела» —
разные диагнозы с разными действиями.

**Содержимое строки не пишется никогда, только её длина и причина.** Плохая строка — самое
вероятное место для чужих данных, а для опознания дрейфа длины достаточно.

У `no_result_line` два исключения, чтобы событие означало именно дрейф, а не норму: убийство
процесса (`cancel_task` и таймаут), где отсутствие `result` ожидаемо и запись на каждую отмену
залила бы лог шумом ровно того класса, от которого событие должно предупреждать; и полная
тишина — CLI, не сказавший ничего, это провал авторизации, модели или спавна, уже видимый по
stderr в записи `finish` и по паттерну `no_progress`.

### Событие `invalid_args`

Вызов отбит проверкой `inputSchema` ещё до хендлера инструмента: SDK сам отвечает клиенту
`MCP error -32602: Input validation error: Invalid arguments for tool …`. Поля: `tool`,
`received` — объект «имя полученного ключа → тип значения» (`string`, `number`, `object`,
`array`, `null`…) — и `message` с текстом ошибки валидации.

Без этого события такой вызов не оставлял в логе ничего и выглядел так, будто до процесса не
дошёл, хотя дошёл. `received` сразу показывает, какого ключа не хватило: `approve_plan` с
`received: {"plan_digest": "string"}` значит, что `session_id` потерялся по дороге к серверу, а
не что клиент прислал пустую строку.

**Значения аргументов не пишутся никогда, только имена ключей и типы.** Через аргументы текут
`task_text` и тела файлов `write_project_file`.

Смежное поле `session_param` в записях `approve` и в отказах `approve_plan`/`execute_task`
говорит, каким именем пришёл идентификатор сессии: `session_id` или синоним `session`. По нему
видно, сработал ли обход прокси, теряющего `session_id` (см. [protocol.md](protocol.md#синоним-session)).

## События файловых инструментов и `run_git`

`file_read` / `file_write`: каталог, относительный путь, размер, `sha256`, а для записи ещё
`existed`, `unchanged`, `previous_bytes`, `previous_sha256` и `created_dirs`. Аудит обеспечивает
связка `path` + `bytes` + `sha256`: пара `previous_sha256` → `sha256` показывает, какая версия
какой сменилась, не храня ни байта содержимого.

`file_list`: каталог, запрошенный `path`, `recursive`, итоговые `count`, `file_count`,
`dir_count`, `truncated`, `truncated_reason`, `scanned`, `unreadable` и параметры фильтра —
этого достаточно, чтобы листинг воспроизвести.

`git_op`: `operation`, каталог, `success`, `git_exit_code`, `duration_ms` и счётчики по
операции — число изменённых файлов и ветка для `status`, `limit` и `count` для `log`, `bytes`
и `truncated` для `diff`, имена веток для `branch_create`/`checkout_branch`, для `add_commit` —
число путей, число файлов в коммите, хеш коммита и **выжимка сообщения** (`message_preview`, по
`logTaskTextChars`). Сообщение коммита — единственный текст, который сюда попадает, и намеренно:
это авторская сводка намерения, которая и так через секунду станет публичной в истории
репозитория, а в аудите «что именно закоммитил мост» это самое полезное поле.

## Что не попадает в лог никогда

Ни при каких настройках: `logTaskTextChars` и `logResultText` на этот список не влияют.

| Что | В каких событиях | Почему |
|---|---|---|
| Содержимое файлов | `file_read`, `file_write` | Через эти тулы течёт произвольное тело файла, то есть самое вероятное место для ключей и паролей (`.env`, конфиги CI), а редактор секретов эвристический и на это не рассчитан. |
| Список путей | `file_list` | Пути менее чувствительны, чем содержимое, но полный листинг репозитория в JSONL на каждый вызов раздул бы лог без всякой пользы для аудита. |
| Содержимое диффа и списки путей | `git_op` | Та же граница, что у `file_list`. |
| Сырой `tool_input` | `hook`, `permission` | Пишется только обрезанная выжимка. |
| Значения аргументов | `invalid_args` | Только имена ключей и типы: через аргументы текут `task_text` и тела файлов. |
| Содержимое плохой строки потока | `stream_warn` | Только длина и причина: плохая строка — самое вероятное место для чужих данных. |
| `last_assistant_text`, `last_tool_call.summary`, `recent_events` | `progress`, `finish`, `timeout`, `cancel` | Записи хуков — это аудит авторизации, где содержимое операции и есть предмет записи, а записи прогресса — телеметрия. Выжимка `Bash`-команды самое вероятное место для секрета в argv, и писать её на каждую сводку значило бы расширить поверхность утечки при нулевой пользе для аудита. |

Реестр задач для `get_task_status` и реестр состояний сессий живут в памяти и только пока запущен
сервер. Долговременная история — в этом логе.

Диагностика сервера идёт в stderr: stdout занят MCP-протоколом, писать туда нельзя.
