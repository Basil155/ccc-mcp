# Фикстуры потока `--output-format stream-json`

Снятые живьём строки NDJSON, которые дочерний Claude Code выдаёт в режиме
`--output-format stream-json --verbose`. Нужны, чтобы разбор потока (сплиттер,
прогресс задачи, детектор паттернов) проверялся офлайн, без живых вызовов CLI
и без трат токенов.

Все три файла сняты **12 сентября 2026 года на claude CLI 2.1.268**, macOS,
модель `claude-opus-5`. Сценарий во всех трёх одинаков: задача просит выполнить
через Bash ровно одну команду `echo hook-stream-test`, а PreToolUse-хук моста
перехватывает вызов. Различается только поведение оператора.

| файл | строк | сценарий |
|---|---|---|
| `stream-denied-retry.ndjson` | 62 | оператор не отвечает; три отказа подряд одному и тому же `request_id` (`b898d1f105d4` на 3.4 с, 56.0 с и 90.3 с), `input` побайтово одинаков |
| `stream-denied-approved.ndjson` | 56 | оператор одобряет на 8-й секунде, повторный вызов проходит |
| `stream-hook-events.ndjson` | 51 | то же, что предыдущий, но CLI запущен с `--include-hook-events`: добавляются `system/hook_started` и `system/hook_response` |

`--include-hook-events` в продукт не идёт (решение A6 основного плана: мост сам
является обработчиком хука и знает о срабатывании раньше и точнее). Фикстура с
этими событиями нужна ровно для одного: доказать, что незнакомые типы событий
разбор не ломают.

## Что видно в этих фикстурах

**Внутри одного процесса CLI несколько пар `init` → `result`.** В
`stream-denied-retry` их три, в остальных по две. Причина — фоновые задачи
(`Monitor`): после `result` приходит `task_notification`, и CLI начинает новый
сегмент со своим `system/init`. Отсюда три следствия:

- `session_id` у всех сегментов **один и тот же** — опознавать сегменты по нему
  нельзя;
- `total_cost_usd` в строках `result` **накопительный** (в `stream-denied-retry`:
  0.2536670 → 0.3161740 → 0.3668295);
- `num_turns` — наоборот, **посегментный** (8, затем 3, затем 2), то есть в
  последней строке `result` лежат ходы последнего сегмента, а не всей задачи.

Правило «побеждает последняя строка `result`» остаётся верным: это ровно та же
семантика, что у режима `--output-format json` сегодня, и `src/parser.ts` из-за
этого не меняется.

**Типы событий, встречающиеся в файлах:** `system/init`, `system/thinking_tokens`,
`system/permission_denied`, `system/background_tasks_changed`,
`system/task_started`, `system/task_updated`, `system/task_notification`,
`rate_limit_event`, `assistant`, `user`, `result/success`, а в
`stream-hook-events` ещё `system/hook_started` и `system/hook_response`.
Ни одной непарсящейся строки в исходных захватах не было (`bad = 0` во всех
трёх прогонах), диагностика CLI уходит в stderr, а не в stdout.

## Санитизация

Исходные захваты лежали во временном каталоге и в репозиторий не переносились.
Замены чисто текстовые, поэтому структура JSON не изменилась ни в одной строке:
число строк, порядок и набор ключей, форма объектов — как в оригинале.

| было | стало |
|---|---|
| `session_id` прогона | `00000000-0000-4000-8000-00000000000{1,2,3}` (своё на файл) |
| прочие UUID (`uuid` события, `hook_id`) | `11111111-0000-4000-8000-<счётчик>` в порядке первого появления |
| `tool_use_id` (`toolu_…`) | `toolu_0001`, `toolu_0002`, … (в том числе в ключах `wire_tool_inputs` и в `permission_denials`) |
| `message.id` (`msg_01…`) | `msg_0001`, … (строка `msg_lifecycle` в `capabilities` — не идентификатор, не тронута) |
| `request_id` API (`req_01…`) | `req_0001`, … |
| идентификаторы фоновых задач | `task0001`, … |
| рабочий каталог замера | `/project` |
| файлы вывода фоновых задач | `/project/.tasks/<task>.output` |
| каталог памяти в домашнем каталоге | `/project/.claude/memory/` |
| `messaging_socket_path` | `/tmp/cc-socks/00000.sock` |

**Сохранено намеренно** — на это опираются тесты:

- `request_id` моста (`b898d1f105d4`, `79b2e8c53379`, `8c8efb0f8e6d`,
  `438bc54d82aa`). Это не случайность, а детерминированный
  `computeRequestId(name, input)` из `src/hookBridge.ts`: одинаковый вызов даёт
  одинаковый отпечаток. Именно поэтому на фикстурах можно проверять счётчик
  повторов и сопоставление с запросами на разрешение.
- Полный текст отказа моста (в `tool_result` и в `hook_response`) — по нему
  проверяется, что содержимое не утекает ни в лог, ни в снимок прогресса.
- Все числа: `usage.*` (включая `cache_read_input_tokens` и
  `cache_creation_input_tokens`, по которым проверяется дедупликация по
  `message.id`), `total_cost_usd`, `num_turns`, `duration_ms`,
  `rate_limit_info`, ISO-`timestamp`, `claude_code_version`.
- Списки `tools`, `skills`, `slash_commands`, `agents` в строке `init`: это
  публичные встроенные имена, и от них зависит реалистичный размер строки
  (~3 КБ).

Проверки санитизации, выполненные при переносе: число строк совпало с
оригиналом, каждая строка парсится, последовательность `type`/`subtype` не
изменилась, в результате нет ни домашних путей, ни имени временного каталога
замера, ни адресов, ни остаточных случайных идентификаторов. Секция `2j` в
`scripts/smoke.mjs` повторяет часть этих проверок на каждом прогоне, чтобы
испорченная или подменённая фикстура падала громко.

## Кто их использует

`scripts/smoke.mjs`, секция `2j` — `NdjsonSplitter` из `src/stream.ts`: разбор
одним чанком, посимвольно и кусками произвольного размера обязан давать
идентичную последовательность событий.

Следующие шаги плана перехода на stream-json добавят на этих же файлах проверки
`parseClaudeOutput` на последней строке `result` и восстановления состояния
задачи по потоку.
